# 供应商管理与账号恢复

## 状态与对外口径

2026-10-05：下述“当前生产措施”通过现有管理员 API 配置；后面的供应商管理模块是设计方案，尚未实现或启用自动调价。

公告、状态页说明、客服通知只描述已核实的用户影响、可用状态和替代线路。不得披露供应商身份、Token 采购、供应商余额或额度耗尽。不得为了隐去内部原因而编造“维护”等原因。供应商诊断仅存于内部管理员界面、内部告警及运维记录；内部告警不能自动复制为用户公告。

公告 11 当前正文仅说明 GPT-6.1 Sol、Claude Sonnet 5.5 上线，以及 Luna / codex-auto-review 的路由与计费，不含内部故障原因。

## 当前生产措施

普通 API Key 账号的 OpenAI 403 会累计，达到三次可进入 `error`。`accountRepository.SetError` 同时将 `schedulable` 设为 false，而 `ClearError` 只恢复 status。这意味着“错误已清除”也不一定意味着恢复了调度。账号测试还有独立的 SetError 路径，不能把定时测试的成功恢复直接当成完整供应商熔断器。

当前优先使用产品已有的池模式及临时不可调度规则，防止普通网关请求把供应商池的一次异常永久固化在本地。

| 账号 | ID |
| --- | --- |
| Shuai-GPT-Pro / CodeRelay-GPT-Pro | 1153 / 1159 |
| Shuai-GPT-Plus / CodeRelay-GPT-Plus | 1170 / 1172 |
| Shuai-GPT-Pro-Special | 1182 |
| Shuai-Claude-Max / CodeRelay-Claude-Max | 1156 / 1166 |
| Shuai-Image | 1165 |
| Shuai-Gemini | 1178 |
| Shuai-Grok | 1180 |

这 10 个账号启用 `credentials.pool_mode=true`，同账号重试最多 1 次，仅对 429/500/502/503/504/529 启用；不对计费或权限错误连续重试。自建 Grok2API 1136 保留原配置。模型映射、价格及凭据未更改。

临时规则按状态码和响应关键词共同匹配：

- 400/402/403/429 中明确的额度、余额或预扣费失败：冷却 10 分钟。
- 403/429/500/502/503/504/529 中明确的限流、过载、超时、无可用渠道等暂态响应：冷却 2 分钟。
- 已知请求模型时沿用模型级冷却，避免把单模型故障扩散到整账号；模型未知时沿用账号级冷却。

冷却到期允许后续真实请求重新尝试，不承诺故障在两分钟或十分钟内修好。池模式不会把所有错误都判定为临时错误；它跳过默认永久账号处罚，未匹配临时规则的响应依旧可能失败。故障详情仍应通过内部运维日志和错误统计观察。

没有创建持续生成内容的定时测试，避免不必要的图像及文本费用。管理员手动测试仍有独立错误状态写入，供应商模块开发时应统一到下述状态机。恢复历史 `error` 账号要先验证实际请求成功，再确认 `status` 与 `schedulable`，不能批量无条件清错。

配置位置：管理员 → 账号 → 编辑 → 池模式 / 临时不可调度规则。回滚时关闭本次新增的池模式及规则开关；本次变更前这些字段均未配置。

验证结果：批量配置 10 成功、0 失败；回读确认其他凭据及模型映射保持原值。1180 的 `grok-4.5` 实际请求返回测试成功，再恢复其历史错误遗留的调度开关。最终 11 个现存账号均为 active 且 schedulable=true。池模式重试与临时隔离相关已有单元测试通过，生产健康接口返回 `status=ok`。这是运行配置更新，没有更换生产镜像。

## 推荐模块范围

第一版做一个管理员“供应商”页面，复用已有账号、渠道和计费能力。供应商代表 Shuai、CodeRelay 等商业来源；平台类型仍代表 OpenAI/Anthropic 等协议，两者不能混为一谈。同一供应商可绑定多个不同权限、价格及分组的账号。

| 页面 | 内容与操作 |
| --- | --- |
| 供应商总览 / 编辑 | 名称、适配器、允许访问的服务地址、关联账号、同步周期、健康状态、最后成功时间、手动同步 |
| 模型与价格变更 | 新增/下线/权限变化、旧价与新价、缓存及阶梯明细、来源、置信度、原始快照、受影响渠道 |
| 调价策略 | 仅监测、生成待审更新、受限自动应用；可编辑幅度上限、延迟生效、模型及渠道范围 |
| 变更记录 | 操作者、来源版本、前后值、生效时间、执行结果、回滚入口 |
| 账号健康 | 冷却原因、下次探测时间、失败次数、最近成功、人工停用、恢复记录 |

供应商凭据继续由现有账号加密存储，供应商记录只引用账号 ID，不复制 API Key。所有新增配置同时交付 Go DTO/API/持久化、Vue 创建和编辑表单、详情展示、校验、中英文文案和行为测试。

## 采集与价格归一化

可复用的现有能力：

- `AccountTestService.SyncUpstreamModelCatalog` 与 `/admin/accounts/:id/models/sync-upstream`：按真实账号权限查询模型并保存能力快照；仅有供应商公开目录不能证明账号可调用。
- `UpstreamBillingProbeService`：探测兼容 Sub2API 的 `/v1/sub2api/billing`，保存账号有效倍率。这个接口不是通用模型价格接口，不能替代 Shuai/CodeRelay 的完整价格卡。
- 渠道模型价格、缓存写入时长、长上下文阶梯、带生效区间的价格版本，以及账号统计专用价格规则。

首批适配器建议为 New API 风格公开价格卡（Shuai/CodeRelay）、Sub2API 倍率、自建/手工价格。支持的 URL 由管理员明确配置，沿用现有 SSRF 和 URL 校验；不要自动跟随目录给出的任意地址。

采集周期建议模型 30 分钟、价格 60 分钟，可手动刷新；增加抖动、并发限制、超时、失败退避和分布式任务锁。超时、空列表、解析失败或权限错误应标为采集失败，保留最后可信快照，不把一次失败认定为模型下线。

New API 的 `model_ratio * 2` 只是普通输入价的换算。存在 `billing_mode=tiered_expr` 时，表达式优先于可能为占位值的 ratios。使用受限解析器识别已支持的变量、算术及分支，不执行任意脚本；不能理解的表达式转为人工核对。

归一化价格必须保留：计费单位、输入/输出、缓存读取、5 分钟/1 小时写入、图片/视频/请求计费、上下文阈值的包含关系、服务档位、生效时区及区间、来源和明确缺失字段。缺失值不是零价。当前 GPT-6.1 Sol 的部分字段来自本地基线，应标记“基线补全”，不能标成“供应商已发布”。

建议持久化实体：`suppliers`、账号的 `supplier_id`、不可变 `supplier_snapshots`、`supplier_changes`、`supplier_sync_policies`、`supplier_sync_runs`。快照保留抓取时间、声明生效时间、内容哈希、适配器版本和清理敏感信息后的原始卡；变更用哈希幂等去重。

## 自动更新边界

默认先自动采集、对比和内部通知，再开放每个供应商/渠道的自动应用策略：

1. 新模型自动进入待发布列表；实际账号可调用、价格完整、渠道映射与规则通过校验后才发布。不能自动扩大 `/v1/models`。
2. 账号成本按其真实供应商卡和有效倍率记录。CodeRelay 与 Shuai 同模型价格不同，应保存到各账号成本规则，不能让“最后同步者”覆盖全渠道价格。
3. 每个渠道明确指定价格基线来源。只有指定来源、完整可信字段、连续两次稳定快照、幅度在管理员设置内的既有模型更新，才允许自动生成并应用价格版本。
4. 用户价格仍由渠道基线与 `groups.rate_multiplier` 决定。自动化不能擅自改利润倍率。应用前模拟各绑定分组的实收与供应商实际成本；存在未经确认的亏损、缺字段、未知表达式、阈值/计费单位变化、大幅涨价或多人并发编辑时转人工处理。
5. 供应商成本按实际生效时间记录；涉及用户扣费的变更采用可配置的未来生效时间和公告流程，绝不回写历史账单或悄悄追溯生效。缓存读写、长上下文、峰谷都由后端按请求开始时间决策。
6. 写入前再次核验原版本，事务性应用；每次保存差异、规则、操作者和执行结果。回滚创建新版本，只影响后续请求。内部变化通知与对外公告分开，公告使用已审核的客户文案。

## 后续统一账号恢复状态机

供应商账号的人工开关、凭据状态和运行时健康状态应分开保存：

`可用 → 暂时隔离 → 单次探测 → 可用 / 延长隔离`

超时、5xx、限流和明确的可恢复业务错误进入临时隔离；优先使用上游可信的 Retry-After/窗口重置时间，否则指数退避并设置上限。模型专属错误只隔离模型；账号共享余额错误隔离账号；供应商级相关故障可合并告警，但不能一次性永久禁用所有关联账号。

到期最多一个 worker 获得探测租约。优先调用能真实证明恢复的轻量接口；仅 `/models` 成功不能证明额度或推理服务恢复。必须生成内容时使用指定廉价模型和预算，图像账号单独限额。探测成功原子解除系统造成的隔离并刷新调度缓存；失败继续退避、内部告警。

明确失效的 Key、权限撤销等单独标记“需要处理”，凭据更新后重验；即使启用低频复测也不得盲目恢复。管理员手工停用始终优先，测试成功不能越权重新启用。历史 `error + schedulable=false` 不能推断成纯系统状态，应给出可预览的迁移/恢复列表。

上线前重点验证：连续暂态失败后恢复、永久凭据失败、人工停用期间探测完成、账号/模型隔离范围、重启后的冷却延续、多实例单次探测、并发价格编辑、空快照/缺字段、长上下文边界、回滚及公告信息隔离。
